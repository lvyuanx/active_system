# ARCHITECTURE-v2 架构交接

任务：TASK-v1 聊天表情包端到端支持架构复核。

输入版本：TASK-v1；本交接由 solution_architect 角色基于冻结任务单和当前已确认实现事实返回，未修改工作区。

状态：completed

结论：

采用增量兼容设计，保持 files service 为唯一媒体信任边界、chat 为消息持久化和规范消息结构的唯一真源；admin、user、screen 只通过接口使用能力，不直接操作文件路径或跨模块数据表。

## 模块边界和数据流

1. admin 在超级管理员和活动条件通过后提交 multipart；files service 在 `chat-stickers` 命名空间中校验真实 Pillow 格式、声明 MIME、宽高、5 MiB 限制、路径和符号链接，再返回随机媒体引用；chat sticker service 在事务中绑定 `activity_chat_stickers`。
2. user 只读取当前活动启用表情，点击后通过既有聊天 WebSocket 发送 `sticker_id`；服务端重新校验活动、用户状态、表情归属和启用状态，写入 `message_type=sticker`、`sticker_id` 和 `[表情] 名称`，再广播规范消息 DTO。
3. chat 历史、`message.created` 和 danmaku HTTP/WS 补齐均通过结构化表情摘要返回。danmaku 只接收受控字段，不接收发送者身份；screen 使用同一消息结构，GIF 由 `<img>` 保持动画，图片失败显示兼容正文。

## 数据库和兼容策略

- 新增 `activity_chat_stickers`，保存活动、名称、媒体 ID、存储 key、MIME、大小、宽高、启用状态和创建时间；活动/启用状态/ID 有索引。
- `activity_chat_messages` 增量增加 `message_type`（默认 `text`）和可空 `sticker_id`；初始化先创建表情表，再使用 `BEGIN IMMEDIATE` 和 `ALTER TABLE` 增加缺失列，不重建或删除历史数据。
- 旧消息按文本解释；表情消息保留 `[表情] 名称`，因此旧客户端可显示占位文本。应用发布顺序为数据库扩展、兼容后端、管理端/移动端/大屏。
- 紧急回滚只回滚应用，不做破坏性 down migration；保留表情表、媒体文件和历史引用。业务止损可统一软下架表情并停止新发送，既有文本聊天保持可用。

## 接口和一致性约束

- 管理端提供活动级列表、multipart 上传、软下架和恢复；用户端列表只返回当前活动启用表情；公开图片以活动、表情 ID 和 `image_id` 版本参数读取，不暴露存储路径或要求管理员凭证。
- WebSocket 只接受合法消息组合：文本使用既有 `body`，表情只使用 `sticker_id`，服务端拒绝文字与表情混合，不接受客户端 URL、MIME 或活动 ID 来替代服务端上下文。
- 消息先提交数据库再广播；广播失败由断线重连后的游标历史恢复。下架只影响新选择和新发送，不删除历史消息或媒体；查询表情时保留历史左连接以继续展示已下架引用。
- 跨活动、不存在、已下架表情统一返回安全的失败结果，避免泄露资源状态；活动 closed/ended、用户 muted/inactive 继续沿用既有只读、禁言和未授权规则。

## 媒体安全和运行性能

- 扩展名和客户端 MIME 均不可信，必须同时通过大小、真实解码格式、图片尺寸、命名空间、路径穿越和符号链接校验；奖品命名空间不接受 GIF，聊天表情命名空间接受 GIF。
- 上传先写临时文件，成功校验后原子移动；数据库写入失败补偿删除媒体。启动和业务操作后的命名空间孤儿扫描只清理过期且无数据库引用的文件，不跟随符号链接。
- 历史查询批量左连接表情，避免 N+1；WebSocket 只传引用和元数据，不传二进制。screen 在入队时根据图片宽高比、当前字体大小和最大显示宽度计算图片宽度，并使用图片宽度与兼容正文宽度的较大值作为统一运动/碰撞/入场占位；加载失败不重新排轨、不破坏 CSS transform 动画。
- 实时和 HTTP 补齐均按消息 ID 合并去重；队列保留现有最大等待和轨道碰撞逻辑，GIF 交给浏览器原生动画渲染。
