# TASK-v1：WebSocket 实时抽奖

任务等级：T6（跨后端、管理端和大屏端；涉及权限、安全、SQLite 并发和高回滚风险）

## 目标

为活动系统增加后端统一中枢的实时抽奖能力。管理端通过管理员 WebSocket 发起开奖和重置，大屏通过公开只读
WebSocket 接收安全事件；配置和历史继续使用 HTTP。开奖必须在数据库事务提交后才广播，并能在并发与网络重试
场景下保持库存和中奖记录一致。

## 用户场景

1. 超级管理员在某活动的抽奖管理页配置奖项、奖品和抽奖规则，查看历史中奖记录。
2. 管理端建立管理员 WebSocket，连接成功后取得快照；多个管理端窗口实时同步开奖、配置和重置结果。
3. 管理员点击“抽取 1 人”后，后端在事务中校验活动、库存、名单和去重规则，提交成功后分别发送管理员完整结果
   和大屏脱敏结果。
4. 大屏建立公开只读连接，收到开奖事件后播放约 3 秒候选名单滚动和中奖揭晓；断线重连通过 `lottery.ready`
   恢复最新状态，不重复播放已揭晓记录。
5. 管理员二次确认后通过 WebSocket 重置中奖记录，大屏同步清空中奖名单。

## 范围

- 后端新增 `lottery` 模块、活动级连接管理器、奖项/奖品/名单/中奖记录/抽奖配置表和增量初始化逻辑。
- 新增管理员配置读写、中奖历史 HTTP 接口；新增管理员和公开大屏两个 WebSocket 路径。
- 实现管理员 JWT 首帧认证、活动隔离、公开端字段脱敏、`BEGIN IMMEDIATE`、`request_id` 幂等和事务内候选人计算。
- 实现 `lottery.ready`、`lottery.draw.result`、`lottery.drawn`、`lottery.draw.error`、`lottery.reset`、
  `lottery.config.updated`、`lottery.ping/pong` 协议。
- 管理端新增抽奖页面和 WebSocket 重连/状态同步；大屏新增深色霓虹抽奖页面、队列去重、断线恢复和揭晓动画。
- 补充后端协议、权限、并发、幂等、恢复、脱敏、重置测试，以及前端队列测试、类型检查、生产构建和视觉验收。
- 同步后端 lottery、参与者注册、管理端活动导航、大屏实时组件和项目知识文档。

## 非目标

- 不实现浏览器端点对点通信、WebRTC 或管理端与大屏端直连。
- 不实现多副本共享消息总线；连接管理器明确保持单进程，后续部署扩展另建任务。
- 不把手机号、黑白名单、活动用户状态或管理员字段发送到公开大屏 WebSocket。
- 不删除活动参与者；重置只删除中奖记录，不清理名单、配置和聊天室数据。
- 不把开奖控制迁移到 HTTP；配置和历史以外的实时控制均走 WebSocket。

## 验收标准

- AC-001：给定管理员登录且活动存在，读取和保存抽奖配置成功，奖项、奖品、数量、名单标记和跨奖品去重规则按活动隔离；历史接口可读出管理员可见的中奖记录。
- AC-002：给定管理员 WebSocket 连接，首帧发送有效管理员 JWT 后收到 `lottery.ready`；缺少凭证、无效凭证、非管理员凭证、活动用户凭证或跨活动凭证均被拒绝。
- AC-003：给定公开大屏 WebSocket 连接，连接成功立即收到同活动 `lottery.ready`；快照及后续公开事件不包含手机号、黑名单、白名单、停用状态、管理员或活动用户 JWT 字段。
- AC-004：给定活动为 `open`、奖品有库存且存在合资格用户，管理端发送 `lottery.draw.request` 后收到完整 `lottery.draw.result`，同活动大屏收到 `lottery.drawn`；中奖数据只有在事务成功提交后才广播。
- AC-005：给定多个管理端同时为同一奖品开奖，数据库事务串行化库存扣减，中奖记录数不超过奖品数量，剩余库存永不为负且广播结果与数据库一致。
- AC-006：给定相同活动和 `request_id` 被重试一次或多次，最多产生一条中奖记录；重试管理端可取得同一结果，不重复广播大屏揭晓事件。
- AC-007：给定黑名单、白名单、停用用户和已中奖用户，候选计算在开奖事务内同时排除不合资格用户；启用跨奖品不重复时同一活动用户不能再次中奖，活动隔离不受影响。
- AC-008：给定活动未开始、已结束、奖品不存在、库存不足或无可中奖者，管理端收到 `lottery.draw.error`，不写入中奖记录，大屏不收到开奖事件且不播放中奖动画。
- AC-009：给定管理员通过 WebSocket 请求重置并确认，中奖记录事务性清空，管理端和大屏收到 `lottery.reset`，大屏中奖名单、序号和库存快照恢复初始状态。
- AC-010：给定管理员通过 HTTP 保存配置，已连接同活动管理端和大屏收到 `lottery.config.updated`，公开消息仅含安全配置；不同活动连接不收到该事件。
- AC-011：给定连接断开后重连，客户端采用指数退避；重连成功收到 `lottery.ready` 快照，已揭晓 `draw_id` 不重复播放，重复事件按 `draw_id` 去重，多条新事件按序列队。
- AC-012：给定管理端和大屏连接存活，`lottery.ping` 得到 `lottery.pong`；连接断开后服务端移除活动房间连接，不影响其他活动。
- AC-013：给定管理端页面，未连接 WebSocket 时开奖和重置按钮禁用并显示重连提示；连接后开奖结果即时更新库存、历史和按钮状态，其他管理窗口结果同步，重置前要求二次确认。
- AC-014：给定大屏收到 `lottery.drawn`，保留深色霓虹、光晕、粒子和滚动候选名单视觉，约 3 秒后揭晓用户名、中奖序号和剩余库存，并展示当前奖项中奖名单。
- AC-015：给定现有活动、参与者、聊天室和弹幕功能，既有后端测试、所有前端类型检查和生产构建继续通过；新增模块文档、任务证据和项目知识同步完成。

## 约束、风险与依赖

- 所有活动数据查询和写入必须带 `activity_id`；管理员可跨活动管理，但不能使用带活动上下文的用户令牌伪装管理员。
- 开奖和重置必须使用 SQLite `BEGIN IMMEDIATE`；不能在事务提交前触发任何客户端广播。
- `request_id` 以 `(activity_id, request_id)` 唯一；重复请求只返回原记录，不再次广播大屏。
- 公开端只能使用安全快照与脱敏中奖事件；管理端完整结果可以包含手机号和加入时间。
- 旧数据库由启动初始化增量创建新表，不批量修改既有参与者；新参与者同步创建默认抽奖名单记录。
- 主要风险是 SQLite 写锁、配置变更与已存在中奖记录的兼容关系、单进程广播限制和浏览器刷新时的动画状态。
- 回滚保留新增表和索引即可；旧应用会忽略新表，已经落库的中奖记录和已递增自增 ID 不因代码回滚自动恢复。
- 运行证据必须保留后端完整测试、前端 typecheck/build、`git diff --check`、受限协议扫描和浏览器视觉截图/检查结果。

## 待确认项

无高影响待确认项。奖项、奖品、名单和去重规则采用本任务架构交接中冻结的字段和 HTTP 形状；多副本消息总线另建任务版本。
