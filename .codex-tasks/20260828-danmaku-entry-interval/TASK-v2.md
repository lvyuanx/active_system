# TASK-v2：多测试用户并发弹幕发送

## 目标

修复真实弹幕测试中“配置 100 人但只有一个发送循环”的问题，使 `user_count` 真正代表并发测试用户数量，形成接近主流视频平台的连续弹幕输入；渲染端继续按轨道容量和不重叠规则控制最终画面。

## 已确认规则

- 每个测试用户拥有独立发送循环，使用自己的用户名/活动用户身份。
- 每个用户首条消息做不超过 1 秒的确定性错峰，避免 100 条在同一瞬间冲击数据库和渲染队列。
- 每个用户之后按现有最小/最大延迟随机等待；管理端参数含义不变。
- SQLite 写入及聊天室/弹幕广播通过单活动发送锁串行化，避免并发数据库锁冲突。
- 测试停止、活动变为只读或发送失败时取消该活动全部用户任务。
- 渲染端继续保留轨道、入场间隔、200 条 FIFO 队列和最大等待丢弃；用户数量不承诺全部同时显示。

## 范围与非目标

- 修改 `DanmakuTestManager` 的调度实现、测试覆盖、管理端说明和模块/项目文档。
- 不改变测试接口字段、聊天室消息协议、弹幕 WebSocket 协议、活动隔离和 token 生命周期。
- 不为“100 人”新增无限队列或关闭渲染端安全保护。

## 验收标准

- AC-010：配置 N 个用户后，N 个用户均会独立产生消息，不再由单循环轮换用户名。
- AC-011：首条消息有短暂错峰，随后各用户按独立延迟循环发送；100 用户配置不会瞬时提交 100 条同步事务。
- AC-012：消息仍写入真实聊天室并广播到聊天室和弹幕通道，发送者身份正确且活动隔离不变。
- AC-013：停止测试、活动关闭或任务异常时，活动下所有发送循环均停止，不遗留后台任务。
- AC-014：管理端仍可设置 1 人以上和 0–60 秒延迟范围，旧请求/默认配置兼容；渲染端继续按安全容量呈现密集弹幕。
- AC-015：后端全量测试、静态回归、类型检查、构建和 Windows x64 打包通过。

## 风险与回滚

- 并发用户数越高，消息写入和广播负载越高；活动级锁只串行化关键写入，用户任务本身仍独立等待。
- 渲染端会丢弃超过容量或最大等待时间的消息，这是保护行为，不代表测试发送失败。
- 回滚为恢复单循环实现，不需要数据迁移或删除历史消息。
