# 架构方案 v1：B站式弹幕碰撞避让

## 方案结论

保留现有弹幕消息补齐、WebSocket 广播、CSS transform 动画、Electron 多屏宿主和 200 条有界队列。将 screen-web 的轨道状态从“固定飞行时长释放时间”改为“活动弹幕几何元数据 + 轨道碰撞预测”，并用 `max_wait_seconds` 控制无法立即入场时的本地等待上限。

## 模块边界与数据流

1. 管理端读取和提交完整弹幕设置；后端服务层校验、持久化并返回完整设置。
2. 现有 `danmaku.settings.updated` 广播携带新字段，screen-web 和 Electron 仅同步类型与会话数据，不新增消息类型。
3. screen-web 在消息进入队列时记录本地 `queuedAt`；队列刷新时测量文本宽度，并以当前配置生成候选运动轨迹。
4. 几何模块计算弹幕在视口内的运动矩形，检查同轨道已有弹幕在候选生命周期内是否发生矩形交叠；无碰撞才允许入场。
5. 入场后的弹幕记录轨道、宽度、开始时间和飞行时长；CSS 负责位移，统一帧调度器只负责入场重试和生命周期回收。
6. 所有轨道不安全时每 50ms 重试；队首消息达到本地最大等待时间后丢弃并继续检查下一条。

## 接口、数据与兼容

- `DanmakuSettings`、`DanmakuSettingsInput`、管理员响应、session 响应增加 `max_wait_seconds: float`。
- SQLite 新表字段为 `REAL NOT NULL DEFAULT 1.5 CHECK(max_wait_seconds BETWEEN 0.5 AND 5.0)`。
- 初始化时检测旧表列，不存在则执行 `ALTER TABLE ... ADD COLUMN`；既有记录自动使用默认值。
- 更新模型中的新字段带默认值 `1.5`，旧客户端省略该字段时后端仍接受并写入默认值。
- 管理端控件为 0.5–5.0 秒、步长 0.1、保留 1 位小数。

## 碰撞算法

- 视口宽度使用当前 overlay 的 `window.innerWidth`；弹幕从 `left = viewportWidth` 移动至 `left = -textWidth`。
- 相同飞行时长下，宽度不同的弹幕速度不同，运动矩形按 `viewportWidth + textWidth` 计算。
- 对候选弹幕与同轨道每条活动弹幕，在两者生命周期交集内检查带 8px 安全间距的矩形是否相交；使用线性运动边界和分段采样/根点检查，覆盖长弹幕追赶短弹幕。
- 轨道从轮询游标开始查找，找到第一个安全轨道后推进游标；不再固定优先第 1 条轨道。
- 配置更新不清空活动项；活动项继续使用创建时的 style/geometry，新项使用新设置。轨道元数据按新轨道数量归并到最近可用轨道，以避免减少轨道数时失去碰撞保护。

## 失败处理、性能与回滚

- 几何函数无浏览器依赖，输入无效时采用有限的最小宽度/时长保护，不抛出影响实时流的异常。
- 队列仍为 200 条有界 FIFO；等待过期只丢弃队首过期消息，不重排后续消息。
- 现有 `task-scheduler.ts` 保持单个 `requestAnimationFrame` 循环；不引入 `setTimeout`/`setInterval`。
- 后端迁移只增列且事务化；代码回滚保留字段，旧版本读取时可忽略新增字段。

## 测试重点

- 后端默认值、旧 SQLite 迁移、合法/非法范围、旧请求体兼容、HTTP 回包和 WebSocket 广播。
- 几何函数的短消息提前入场、8px 间距、长消息追赶、不同宽度和轨道轮询。
- screen-web 类型检查、构建、现有消息排序/任务调度回归和高频队列静态/浏览器行为回归。

## 任务执行方式

本次输入工作树已有未提交改动且共享 SQLite、pnpm 缓存和本地运行资源，隔离 worktree 资格不满足；主 Agent 采用 `SERIAL_SHARED_WRITE`，单一集成者直接在主工作树修改，保留输入快照和逐阶段证据。
